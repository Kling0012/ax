# テスト設計の手順書

S-16.2 の `docs/test-procedure.md`。ワーカー（役割 `test_design`）と実装者がテストを書くときに従う。

## 数の上限

- 1件の変更に書くテストは、S-17 `test_cases_max`（既定 12、範囲 3〜30）件まで。
- 数を増やして安心しない。守る振る舞いを絞り、重複するテストは書かない。

## 例を先に書く

- 受け入れの例（すべきこと）と境界の例（してはいけないこと）を、どちらも書く。
- 閉じる・止める・送る・通知する処理を変えるときは、してはいけない例を必ず入れる。
  - 例: 「期限が来ても自動で解除しない」「拒否した指示を実行しない」「送れないときに処理を止めない」。
- 依頼の `acceptance.examples` と `acceptance.boundaries`（S-7.10）がそのままテストの見出しになる。

## 1テスト1つの振る舞い

- 1つのテストで確かめる振る舞いは1つ。名前は振る舞いを文にする（`test_<対象>_<条件>_<結果>`）。
- 準備が長いときは、準備を fixture に出す。テストの本体は操作と確認の数行にする。
- 確認は具体的な値で行う。「例外が出ない」だけの確認で済ませない。

## 外部に触れない

- ネットワーク、実サービス、実際のモデル、実際の docker・systemd・ssh・sudo を使わない。
- 外部の相手は `tests/fakes/` の偽の部品に置き換える（偽のモデルの入口 `model_gateway.py`、偽の HTTP `http.py`、偽の時計 `clock.py`）。
- `tests/conftest.py` は、試験中のソケット接続を拒否する。偽の部品はソケットを使わない。
- 一時ファイルは `tmp_path`（`TMPDIR` の下）を使う。`/tmp` やホームに書かない。
- 実環境でしか通せない試験は、`realenv` の印を付けて CI から外し、`status/<束の ID>.md` の表に「未実行」と理由を残す。

## 意図した理由で赤になる

- 実装の前に、そのテストが赤になることを確かめる。赤の理由は確認の失敗（`assert` の不一致）であること。
- 構文の誤り、import の失敗、fixture の不足で赤になっているテストは、意図した赤ではない。直してから実装に進む。
- 秘密の形をした値は試験のソースに実値で書かない。実行時に文字列を連結して作る（S-15.3。公開検査と gitleaks に当たるため）。

## 実行

- 変更した部分だけ確かめる: `python3 -m pytest -p no:cacheprovider tests/<束の ID>`。
- 全体は `tools/ci.sh`（F-14.1）。全テストをワーカーの中で回さない。フル実行はパイプラインに任せる。
