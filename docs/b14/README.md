# 変更受付

変更受付は `change` プラグインとして登録する。サービス名は `sl-change` とする。
収集、安全審査、質問への回答、変更の検証、マージ、公開待ちへの引き渡しをグラフでつなぐ。

起動時のモードは `collect_only`、`dry_run` の既定値は `true` である。
`dry_run` を省いた呼び出しは予定とノートだけを返す。
収集だけのモードでは作業者も検証も起動しない。

実装の変更には共通の部分グラフ `tdd-change` を使う。
質問だけの経路は安全審査の後に調査と回答を行い、検証やマージには進まない。

## 接続

登録は `plugins/registry.d/b14.yaml` に置く。
Compose のサービス定義は `compose.d/sl-change.yaml`、共有の秘密の宣言は `compose.d/b14.yaml` に置く。
コンテナは `ax-work` だけに接続し、ホストへの待受ポートを持たない。

`AX_CHANGE_PORT_FACTORY` は配備側が指定する `module:factory` である。
関数は `factory(services=..., journal=...)` の形で呼ばれ、`integration.ports.Ports` を返す。
Issue、PR、コメント、項目データから factory を選んではならない。
未設定なら、このプラグインだけを起動不可として状態に表示する。
架空の API や成功する代用品には切り替えない。

収集、安全審査、検証の接続には `integration.adapters.create_ports` を使う。
実際の外部クライアント、通知、カード、公開待ちの接続は配備側の factory が渡す。
公開待ちへの引き渡しは公開の実行や Issue の完了を意味しない。

## マージの条件

マージの直前に、コメント、要求一覧、検証済みの完全な head SHA、指定 CI、競合、権限を再照合する。
書き込みにも同じ SHA を期待値として渡す。
指定 CI がない、古い SHA である、外部 PR 自身の workflow しかない場合は通さない。
CI を持たない対象は登録済みの `ci_sources: []` と検証の証拠を使う。

未信頼 PR には継続許可だけを適用しない。
独立した二者の安全審査と同じ head での collect_only の確認を先に要する。
その後、対象のカードで利用者の個別指示を待つ。
マージ予定の通知が配送された時刻から30分待ち、直前の条件を再照合する。
待機中も別の項目は進む。

修正や競合解消の後は、新しい head で安全審査と検証をやり直す。
標準 `tdd-change` は再入場の上限20を使うため、外側に追加の循環辺を置かない。
修正回数を保存して項目を再試行待ちへ戻し、次の入場で部分グラフを通す。
修正回数は入場ごとにリセットしない。

実装 PR が未作成の案件では、候補 head の完全な検証証拠と要求の完了を確認してから、登録済みの実装先へ PR 作成を配送する。
配送結果の repo と PR 番号が実装先に一致する場合だけ採番を取り込み、マージ直前の条件をあらためて照合する。
