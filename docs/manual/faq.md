# よくある質問：AX の仕組みと使い方

## 1. 承認

### Q1. なぜ戻しにくい操作は利用人本人だけが承認するのですか

戻しにくい操作は実行者自身では決められないためである。司令塔の受け口、エージェントの文章、`GO.md` のような司令塔が書いたファイルでは、承認の代わりにならない。そのため、承認は HQ で利用者本人が行う。段が `irreversible` の席でも、依頼しかできない。依頼は承認待ちになり、実行されない。

### Q2. 承認の仕組みはどうなっていますか

司令塔が `tier: irreversible` の行き先へ指示を送ると、入口は実行しない。内容と `digest` を保存し、`approval.requested` を書く。応答は HTTP 202 で、`ax` の終了コードは4である。台帳にカードが作られる。利用者が HQ の承認画面で全文を読み、第二要素を入れて承認する。入口は `digest` が一致し、期限内であることを確かめてから、保存した内容を実行する。承認は1件に1回だけ使える。期限切れ、却下、取り下げ、依頼した席の失効、`lockdown` の間は実行しない。

### Q3. 司令塔が「承認済み」と言っても進めないことがありますか

ある。`confirm_irreversible` は、`from=hq` で承認 ID が付いた指示だけが `true` を持てる。司令塔の受け口の本文に `confirm_irreversible: true` があれば、承認待ちにせず `forged_authority` で拒否する。席の段が `tier` に足りなければ、`tier_insufficient` で拒否する。

### Q4. 継続許可とは何ですか

対象 repo・公開先・操作が一致する利用者の継続許可がある場合、従来どおり承認を要しない。許可の作成と無効化は `irreversible` である。司令塔が許可を増やすことはできない。照合が不明なら拒否する。

## 2. 安全と失敗の扱い

### Q5. なぜ fail-closed なのですか

許可が不明なときは実行しないためである。新しい操作の種類を継続許可だけで実行しない。二者の安全レビューと利用者の個別承認を要する。席の台帳が読めないときは、最後に読めた版を使う。一度も読めていなければ、席をすべて拒否する。表が無い、読めないときは全部拒否する。閉じる側に倒す。AX の他の機能は止めない。

### Q6. 許可が不明な操作はどうなりますか

拒否する。他の安全条件も満たす。許可の照合が不明なら拒否し、他の安全条件も満たす。対象が不明な処理は行わない。分岐を設けない。新しい公開ポートを作らない。

### Q7. 秘密や個人情報が入った文章はどう扱いますか

送らない。秘密検査（S-15.3）を通す。鍵・トークンの形、秘密置き場の値との一致、個人情報を見る。時系列記録は `[REDACTED]` に置き換えて書く。記憶コネクタと `gate.secret_scan` は、当たったら拒否する。通知は送信前に秘密と個人情報を検査し、含む場合や検査不能の場合は送らず失敗を記録する。

### Q8. 故障した部品は全体を止めますか

止めない。障害を当該機能に閉じ込める。1つのホスト・1つの手順が失敗しても、他の手順は止めない。止まった手順は ToDo カードに出す。特権操作が使えないときは、その周期の特権操作だけを行わず、観測、通知、入口、台帳、サブループなど他の機能は止めない。

### Q9. 外部の文章が指示にならないのはなぜですか

外部の文章はデータであって命令ではないためである。指示の `payload` の文字列はデータとして扱う。`from`、`principal`、`issued_by`、`confirm_irreversible`、`approved_via`、`tier` に当たる名前を、Schema にない場所に持つ指示は `forged_authority` で拒否する。行き先の Schema は `additionalProperties: false` とする。

### Q10. 監視の空白は起きますか

起きる。AX では監視を最初に立ち上げる。監視の空白は許す。起動し直した場合は、起動し直した時刻から数え直す。

## 3. 資源と上限

### Q11. 資源が尽きたらどうなりますか

その系統の新規起動だけを停止する。その系統を要し、他に条件を満たす候補がないジョブは `parked` の ToDo カードで待たせる。復旧確認後に対象ジョブを再開し、他の系統とジョブは継続する。コストの比率や系統別・日別の費用上限の数値は設けない。

### Q12. 満枠のときはどうなりますか

最安候補が満枠なら枠を待つ。役割別待機列は `role_queue_max` までとし、超過は `skipped(queue_full)` とする。モデル・系統の同時実行枠は選択直前に再確認し、原子的に枠を確保する。満枠だけでは失敗回数を増やさない。

### Q13. 受付が満杯のときはどうなりますか

`inbox` が `inbox_max` に達していれば `429`（`inbox_full`）を返す。入口は ToDo を `parked`（理由 `inbox_full`）にする。同じ `item_key` は1回だけ受け付ける。2回目は受付済みを返す。

### Q14. 上限の値は誰が変えますか

利用者が値を変更する。管理役は変更を提案するだけである。変更は実行中のジョブを止めず、次の枠取得から適用する。`0` は新規起動停止を意味する。初期上限は AX の設定で決める。

## 4. モデル

### Q15. モデルはどう選ばれますか

登録モデルを状態、役割の最低段階、情報区分、画像と用途に必要な能力で絞る。Jev が適合と判定した候補から最安を選ぶ。Jev が使えないときも適格な候補から最安を選ぶ。GPT・Claude は、モデル説明が難しい用で作業に合う場合、または同じ作業で安いモデルが2回失敗した場合だけ候補に残す。利用制限・quota・接続障害・保留は能力上の失敗に数えない。

### Q16. 「最安」とはどういう意味ですか

`flat`（定額・quota 型）の候補は追加費用なしとして、tier の順、同じ tier は役割の順、同順位は ID 昇順で比べる。`metered` の候補は単価で比べ、`flat` の候補より後に置く。`metered` で単価が未登録の候補だけが残る場合は、対象ジョブを保留する。定額の候補があれば保留にしない。

### Q17. 無料モデルはどう扱いますか

新しい無料モデルは L1 から始める。同じ段階の実作業で `promote_after` 回連続合格なら1段上げ、`demote_after` 回連続不合格なら1段下げる。合否は `verify.cmd`・関門による検証で決める。利用制限・quota・接続障害は合否に数えない。昇格だけの試験は作らない。実作業の `promotion_share` を上限として、検証可能な1段上の実作業を昇格の候補に割り当てる。

### Q18. 予備役はどのモデルですか

予備役は Sonnet 5.5 だけである。Opus は自動経路に入れない。自動化での Claude 系は予備役の Sonnet 5.5 と `test_design` の最後の手段の Sonnet 5.5 に限る。

### Q19. 司令塔に使えるモデルはどう決まりますか

司令塔のモデルと提供元は、`config/commander-models.yaml` に載っていること。`operate` 以上の段を使えるのは、能力段階 L3 以上で、道具呼び出しの引数を壊さずに書けると確かめたモデルだけである。確かめるには司令塔試験に合格する。試験の結果がない、古い、またはモデル名が結果と合わないときの有効な段は `read` である。

## 5. 停止と再開

### Q20. AX を一時停止するにはどうしますか

動作モードを変える。`collect_only` は巡回と記録だけを行い、新しい項目を起動しない。`poll_paused` は巡回をしないが、待っている項目は起動する。`draining` は巡回をしないが、実行中の物を最後まで続ける。モードを変えても、実行中の物は止めない。止めたいときは `cancel` 命令を使う。制御命令は `ax control <target> <op> [args] --reason ..` で出す。緊急の停止は HQ の緊急ボタンである。

### Q21. 個別の作業を止めるにはどうしますか

利用者は作業またはワーカーを ID で個別に停止できる。処理を中止すると理由、状態、途中成果物と再開に必要な参照を保持する。対象を指定して再開できる。再開は既存の作業と関連付け、検証や権限を再確認する。停止・再開失敗は対象の状態を成功に変えず、理由を表示し記録する。他の作業は止めない。

### Q22. 緊急ボタンはどう動きますか

範囲は `all`、`commanders`、プラグインの ID のどれかである。`commanders` は司令塔の受け口だけを対象にし、`lockdown` を行う。`lockdown` は、すべての身元の段を `read` に下げ、生きている `issued_by=commander` の命令と保持を外し、承認待ちを止め、`seat.lock all` をかける。解除は HQ の操作だけである。記録はスナップショットとして退避先に置く。実行中のコンテナの起動し直しは、ホスト見張りが `sudo -n` で行う。

### Q23. 席を止めるにはどうしますか

席の失効は `seat.revoke` で行う。他の席の失効を司令塔の受け口から行うことはできない。`seat.lock` で範囲の受け口を閉じる。HQ とローカルの `ax` は影響を受けない。解除は `seat.unlock` で行う。自動停止は、1つの席が `commander_rate_window_min` 分の間に `commander_rate_max` を超える指示を出す、または拒否が `commander_reject_suspend` 回続くと、その席を `suspended` にする。

## 6. データと秘密

### Q24. 情報の区分はどうなっていますか

| 区分 | 例 | 渡してよい先 |
|---|---|---|
| `public` | 公開リポジトリ、公開の文書 | すべてのモデル、すべての実行環境 |
| `private` | 非公開リポジトリのコード | 登録済みのモデル。`data_classes` が `private` を許す実行環境。`cloud-sandbox` には渡さない |
| `sensitive` | 基盤の設定、サーバーの中身、利用者の個人情報が混じる物 | `tier` が `standard` 以上の登録済みのモデルだけ |

利用者が登録したモデルと提供元は、それだけで送ってよい許可とみなす。学習利用は送り先の条件にしない。登録されていないモデルや提供元へは送らない。非公開コードを扱える実行環境は、台帳の `data_classes` が `private` を許す登録済みの環境に限る。登録・権限を確認できなければ非公開コードを渡さない。

### Q25. 秘密はどこに置きますか

ホストの秘密置き場に置き、compose の secrets で、manifest の `secrets` に書いた物だけを読み取り専用で渡す。イメージ、git、時系列記録、ToDo、記憶に、秘密の値を入れない。秘密が要る件は、ToDo カードで HQ の秘密の受け口を案内する。受け口は書くだけで、値を画面に出さない。

### Q26. 退避はどういう仕組みですか

各部品は古い記録や成果物を自分のボリュームの `archive/` に置く。退避コネクタは `archive_after_days` 日より古い物を退避先へコピーし、コピー先で内容ハッシュを再計算し、元の内容と照合する。内容が一致したときだけ元を消す。検証不能、失敗、不一致のときは元を保持し、失敗を記録する。内容の照合を実装して試験を通すまで、元を消す動作は有効にしない。削除の API は持たない。

### Q27. 退避の元の除去を止めるにはどうしますか

止めるのは切り替えの実施者だけである。止める前に、確認済み manifest の一覧を撤去の archive へ写す。印 `${ax_state_dir}/archive/reap-enabled` をその archive へ移す。`host/ax-archive-reap.sh` は印がない間は何もしない。止める条件は、緊急の停止と、退避の途中に不整合が見つかったときに限る。通常の巡回では止めない。戻すときは印を戻し、manifest の再確認から始める。

### Q28. 通知はどう届きますか

通知は自前の非公開サービスから配信する。利用経路は profile の `ntfy_endpoint` の `POST` で、topic は profile の `ntfy_topic` である。送れるのは `ax-core` の網の部品だけである。`ax-work` と `ax-job` のコンテナは届かない。通知先への失敗は時系列に記録し、他の処理を止めない。通知のボタンでは承認できない。

## 7. 実行環境

### Q29. ホストを追加するにはどうしますか

新しい環境の追加は台帳の項目の追加であり、本体のコードを変えない。手順は次のとおりである。テンプレートの複製、manifest の記入、導入、`probe`、台帳への登録（`state: trial`）、試行の作業、有効化（`available`）である。変更するのは設定の項目だけである。登録と有効化は利用者の指示と `core.change` だけで行う。初日の環境も同じ手順を通す。

### Q30. 環境に必要な物は何ですか

環境の側に置く物は、manifest、`ax-env-run`、`probe`、入口の定義、導入・更新・取り外しの手順、結果とログの形式である。秘密の値は含めない。`ax-env-run` の口は `submit`、`status`、`logs`、`fetch`、`cancel`、`lookup`、`release`、`probe`、`validate`、`version` である。本体のアダプタはこの口だけを呼ぶ。任意のコマンドは送らない。

### Q31. 箱（cloud-sandbox）はどう扱いますか

箱は AX の部品が使うツールである。用途は次の3つだけである。隔離した実行（秘密を含まない作業）、公開 Web の画面操作とスクリーンショット、Windows 以外の画面作業である。箱の削除・破棄の操作は持たない。箱の作成は利用者が提供元で行う。能力は `probe` で確かめる。確認できていない能力は `unverified` にし、その能力を要る作業だけが `parked` になる。

### Q32. Windows の画面作業はどうしますか

Windows の Computer Use は環境ではなくツールとして扱う。環境の自動の選び方にも、ワーカーの候補にも出さない。使うのは、利用者の指示、またはツールの ID を名前で明示した呼び出しだけである。行き先を明示しない依頼は拒否する。

## 8. 運用と文書

### Q33. ライセンスと公開状態はどうなっていますか

この文書の時点では、ライセンスは未定である。変えてよい範囲の変更は利用者が決める。リポジトリは非公開のままである。`docs/CHANGELOG.md` に変更の記録を残す。受け入れ試験がすべて通った状態をタグ（`vX.Y.Z`）で保存する。

### Q34. 司令塔とワーカーの違いは何ですか

司令塔は役割であり、動かすハーネスとモデルは問わない。司令塔の手引きは正本1つから各ハーネスの形式へ生成する。`tools/gen_commander_guide.py` が `dist/commander/` に作る。無人で繰り返し動く物は司令塔ではなくサブループにする。

### Q35. ToDo の状態はどうなっていますか

状態は `todo`、`running`、`review`、`waiting_user`、`parked`、`done`、`dropped` の7つである。`waiting_user` にできるのは、理由が決まった場合だけである。`irreversible`、`publish`、`money`、`secret_input` のカードは `user_only` で固定である。司令塔の中継の回答はできない。

### Q36. 判断の記録はどう残しますか

司令塔の方針・好み・引き継ぎメモは、台帳に追記だけで残す。変更は新しい行を足す。前の行は `superseded` になる。更新と削除の API はない。司令塔が「利用者がこう言った」と記録した物は `attested: false` で、戻しにくい操作の根拠にならない。
