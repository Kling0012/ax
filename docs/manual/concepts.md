# 用語集と概念

この文書は AX で使う言葉を定義します。

> 概要（3行）
> AX は「入口で受け」「台帳で待たせ」「サブループで進める」ことで動く道具です。司令塔は対話の席、席は段を持つ接続です。戻しにくい操作は本人の承認だけが通します。

## 用語集

各用語の意味を以下に示します。

| 用語 | 定義 |
|---|---|
| 司令塔 | 利用者と会話する対話セッションの役割。動かすハーネスとモデルは問わない。ループしない。入口だけを使う。同時に複数いてよい |
| 受け口 | 入口が指示と照会を受ける口。`local`、`ssh`、`tailnet`、`hq` の4つ |
| 席 | 司令塔の1つの接続の資格。1台の端末と1つの資格の組。段と期限を持ち、席ごとに失効できる。席の ID と身元の ID は同じ |
| 段 | 席の権限。`read`（読むだけ）、`operate`（運用）、`irreversible`（戻しにくい操作の依頼。実行の資格ではない） |
| 承認 | 戻しにくい指示を、AX が保存した内容そのものに対して、利用者本人が HQ で許す記録。段ではない |
| 保持 | 対象への運用の操作を、ある司令塔が一時的に持っている状態。期限で自動で外れる |
| サブループ | スケジュールで永久に回る、管理下の自動化。中身はグラフ |
| タイマー | 管理役が作れる、ノードが1つだけのプラグイン。決まった時刻に1つの作業を起こす |
| 実行（run） | サブループの1周回 |
| 項目（item） | 1回の実行の中で扱う1件（例: Issue 1件） |
| 外へ出す（eject） | 項目か実行を止め、台帳へ移すこと。所属するサブループは回り続ける |
| 制御命令 | プラグインの動作モードや調整項目を変える命令 |
| 調整項目 | プラグインが宣言した、型と範囲を持つ変更可能な値 |
| 点検 | 新しい起動を止め、見直しと恒久修繕を行う時間 |
| 実行環境 | 作業を走らせる、AX の外の場所。能力と区分と上限などを台帳に持つ |
| 環境モジュール | 実行環境の側に置く `ax-env-run` と manifest と入口の定義と導入手順の一式。テンプレートから作る |
| 能力 | 環境ができることの名前（例: `steam-workshop-upload`、`gpu`）。作業は環境の名前ではなく、能力で環境を選ぶ |

## 1. 動作の単位

### 1.1 項目（item）

1回の実行の中で扱う1件です。例は Issue 1件です。項目は `item_id` と `todo_id` と一緒に扱います。

**例**：変更受付のサブループが Issue 1件を拾う。項目は1件になる。

### 1.2 実行（run）

サブループの1周回です。実行には状態があります。

```text
planned → launching → submitted → running → completed
                                           → failed(reason)
                                           → timed_out
                                           → cancelled(by)
                                           → lost
planned → skipped(reason)       （mode やモデル不足で起動しなかった）
任意の状態 → ejected(reason)     （外へ出した）
missed                          （予定の時刻に起動できなかった。後から追いかけて実行しない）
```

### 1.3 外へ出す（eject）

項目か実行を止め、台帳へ移すこと。所属するサブループは回り続けます。

### 1.4 サブループ（subloop）

スケジュールで永久に回る管理下の自動化です。中身はグラフです。

**例**：標準の `work-tdd` は入口の実装依頼をテスト駆動で進める。

### 1.5 ノード（node）

グラフの1ノードです。ノードの実装を部品庫と言います。部品庫の型は `plugins/nodes/` に置きます。

**例**：`gh.list_issues` は Issue を項目にする。`worker.run` は worker-pool にジョブを出す。

### 1.6 制御命令

プラグインの動作モードや調整項目を変える命令です。命令は期限を持つことがあります。期限を過ぎても宣言した動作を続けます。解除と延長は、出した者が行います。

命令の形です。

```json
{
  "id": "01J...",
  "target": "issue-automation",
  "op": "set_mode",
  "args": {"mode": "collect_only"},
  "reason": "点検の30分前。新しい実装の起動を止める",
  "issued_by": "manager",
  "issued_at": "2026-11-05T12:00:00.000Z",
  "expires_at": "2026-11-05T13:00:00.000Z",
  "on_expiry": "ask_issuer",
  "corr": "01J..."
}
```

| 項目 | 意味 |
|---|---|
| `target` | 変える対象のプラグインの ID |
| `op` | 操作の名前（`set_mode`、`set_knob`、`exclude_resource`、など） |
| `args` | 操作の引数 |
| `reason` | 理由。空でないこと |
| `issued_by` | 出した者の種別（`user`、`commander`、`inspection`、`manager`、`backup`、`emergency`） |
| `expires_at` | 期限。出席者は `user` 以外は期限が必要 |
| `on_expiry` | 期限切れの扱い（`ask_issuer` か `release`） |

**例**：管理役は1プラグインへ1つの命令を期限付きで出す。中核の部品への命令は受け付けない。

### 1.7 調整項目（knob）

プラグインが宣言した、型と範囲を持つ変更可能な値です。宣言は `manifest.yaml` の `knobs` に書きます。

| 項目 | 意味 |
|---|---|
| `type` | `integer`、`number`、`boolean`、`string`、`enum`、`duration`、`list` |
| `default` | 既定値。範囲の中にあること |
| `min`、`max` | 数値の範囲 |
| `enum` | 選べる値 |
| `effective` | 効く時刻（`immediate` はすぐ、`next_run` は次の実行から、`restart` は再起動で） |
| `title` | 日本語の説明 |
| `who` | 変えてよい発行者の一覧。省略時は全員 |



### 1.8 作業側の口

中核の部品が ax-work の網へ開ける許可した API の口です。時系列記録は追記と読み取りを通します。台帳は ToDo の作成と読み取りを通します。制御 API は登録と有効な値の読み取りだけを通します。遷移と回答と命令の発行は通しません。

## 2. 席と段

### 2.1 司令塔（commander）

利用者と会話する対話セッションの役割です。動かすハーネスとモデルは問いません。ループしません。入口だけを使います。同時に複数いてよいです。

**例**：同じホストで複数の司令塔が同時に動きます。席が違うと衝突しません。

### 2.2 席（seat）

司令塔の1つの接続の資格です。1台の端末と1つの資格（SSH 公開鍵か tailnet のトークン）の組です。段と期限を持ち、席ごとに失効できます。席の ID と身元の ID は同じです。

席の台帳は1つです。席を変えられるのは入口だけです。

### 2.3 段（tier）

席の権限です。3つに分かれます。

| 段 | できること |
|---|---|
| `read` | 読むだけ |
| `operate` | 取り消せる運用の指示 |
| `irreversible` | 戻しにくい操作の依頼。実行の資格ではない |

段が高い席でも、承認は出せません。`irreversible` の段の指示は承認待ちになります。実行されません。

### 2.4 保持（claim）

対象への運用の操作を、ある司令塔が一時的に持っている状態です。期限（lease）で自動で外れます。

対象の鍵は行き先ごとに決めます。例は `control:{target}:{op}:{args.name}`、`card:{todo_id}`、`todo:{todo_id}` を定義します。

保持がある間、別の席の食い違う指示は止まります。先の指示は変えません。後から来た方を止めます。

保持は権限ではありません。持っていても段は上がりません。

**例**：編集中の対象に別の司令塔が操作を出す。保持の持ち主と違うと、後から来た方が止まる。

### 2.5 依頼 ID（request_id）

運用の依頼を1回だけにする印です。`idempotency_key` が必要な行き先で使います。同じ値は1回だけ処理します。再送したときは前の結果を返す。内容が違えば衝突します。状態を変える指示は固定値で再送できます。

## 3. 記録と待ち

### 3.1 ToDo 台帳

ToDo は利用者を待つカードです。台帳にカードとして残します。カードの中に質問と選択肢と回答があります。

ToDo の状態遷移は表で固定されています。表にない遷移は拒否します。

| 状態 | 意味 |
|---|---|
| `todo` | まだ誰も持っていない |
| `running` | ワーカーかサブループが持っている |
| `review` | 結果の確認待ち |
| `waiting_user` | 利用者の回答待ち |
| `parked` | 外へ出された。理由と次に見る時刻を持つ |
| `done` | 完了 |
| `dropped` | 不要になった |

### 3.2 利用者だけのカード（`user_only`）

理由が戻しにくい操作、公開、お金、秘密入力のカードは `user_only` で固定します。司令塔の中継の回答はできません。

**例**：戻しにくい操作を尋ねるカードに司令塔が答える。403 で拒否される。

### 3.3 時系列記録（timeline）

追記だけの事象の記録です。書き換えと削除の API を持ちません。状態の表示用データは事象を先頭から読み直すと再現できます。

主な事象です。

| 事象 | 誰が書くか |
|---|---|
| `instruction.received`、`instruction.routed`、`instruction.rejected` | 入口 |
| `control.issued`、`control.applied`、`control.released` | 制御 API |
| `run.state`、`item.state`、`node.state` | サブループ |
| `job.state` | worker-pool |
| `task.state` | 台帳 |
| `resource.state` | 資源台帳 |
| `error.classified` | 各部品 |
| `health.beat` | 各部品 |
| `health.alert` | オブザーバー |



### 3.4 外部への送り出し待ち行列（outbox）

時系列記録や記憶コネクタに届かないとき、送る側は自分のボリュームに溜めます。送り出し待ち行列（`outbox/`）に溜めます。届くようになったら順に送ります。届かないことを理由に自分の処理を止めません。

### 3.5 判断の記録（decision）

司令塔の方針と好みと引き継ぎメモを台帳に追記だけで残します。種類は `decision`（決まった方針）、`preference`（利用者の要求と好み）、`handoff`（次へのメモ）があります。HQ の利用者本人の操作で記録したものだけ `attested: true` です。司令塔の申告は `attested: false` です。印が `false` の記録は、戻しにくい操作の根拠になりません。

## 4. 実行の形

### 4.1 worker-pool

ワーカーのジョブを受け、役割に合うモデルを選び、同時実行数を守って起動と監視と検証を行い、結果を返します。

worker-pool の役割は `config/roles.yaml` に置きます。

| 役割 | 用途 | 最低段階 |
|---|---|---|
| `summary` | 要約と整理 | L1 |
| `research` | 読むだけの調査 | L1 |
| `second_opinion` | 異なる系統の第二意見 | L1 |
| `screen` | 判定と分類 | L1 |
| `assist` | 検証付きの軽い作業 | L2 |
| `test_design` | テスト設計 | L3 |
| `impl` | 実装 | L3 |
| `impl_hard` | 難しい実装 | L4 |
| `review` | 審査 | L3 |
| `review_final` | 最終審査 | L4 |
| `manager` | 管理役の判断 | L3 |
| `backup_manager` | 予備役 | L4 |

役割の最低段階と利用可能系統と情報区分で候補を絞ります。選んだモデルの同額時の既定候補の順を置きます。順序付き一覧は適格候補を限定しません。

試行は各回にあります。試行にはモデルと開始と終了時刻と結果と検証結果と切替理由を対応付けます。



### 4.2 ジョブ

ジョブは新しいコンテナで実行します。書き込めるのは作業場所だけです。秘密は manifest に書いた物だけ渡します。通信は許可先だけです。

**例**：サブループの `worker.run(impl)` がジョブを出す。worker-pool がモデルを選び、ジョブ用コンテナを起動する。

### 4.3 実行環境（environment）

作業を走らせる AX の外の場所です。能力と情報区分と上限と費用と寿命を台帳に持ちます。

環境の種類です。

| 種類 | 形 |
|---|---|
| `local` | 実行ホスト自身。ループバックの SSH で入る |
| `ssh-host` | 別のホストへの SSH |
| `container` | 別の位置のコンテナ |
| `cloud-sandbox` | クラウドの使い捨て箱 |

能力は `capabilities` の一覧です。例は `steam-workshop-upload`、`gpu`、`docker`、`archive-store` です。依頼は環境の名前ではなく、必要な能力で書きます。

環境の選び方は順序がありました。能力、区分、空き、費用、`rank`、その日の利用時間、登録順です。

環境は監視が常駐の検査（`resident_check`）や `probe` を行います。環境の状態は `state`（`trial`、`available`、`degraded`、`excluded`、`draining`、`retired`）で表し、理由と期限を持ちます。

### 4.4 環境モジュール（env module）

実行環境の側に置く `ax-env-run` と manifest と入口の定義と導入手順の一式です。テンプレートから作ります。

環境側の物は `ax-env-run`、manifest、`probe`、入口の定義、導入と更新と取り外しの手順、結果とログの形式を含みます。秘密の値は含みませんし、本体は契約（S-25.12）だけを持ちます。

環境モジュールのテンプレートは `templates/env/` にあります。

## 5. 資源と選び方

### 5.1 ランナー（runner）

モデルを呼ぶ CLI か HTTP の起動方法の名前です。例は `agent-cli`（モデルの入口を経由してコード作業の CLI を動かす）、`chat-json`（判定だけの HTTP 呼び出し）です。

起動の雛形は `config/runners/<名前>.yaml` に置きます。イメージ、起動コマンドの雛形、渡す秘密の名前を書きます。

### 5.2 役割（role）

用途ごとの仕事の名です。例は `impl`（実装）、`review`（審査）、`manager`（管理役の判断）です。役割には最低段階と候補の順があります。`config/roles.yaml` を見てください。

### 5.3 能力段階（level）

性能の段階です。L1 から L4 まであります。

| 段階 | 初期値 |
|---|---|
| L1 | 新しい無料モデルは L1 から始める |
| L2 | 軽い作業 |
| L3 | 実装まで |
| L4 | 難しい実装と最終審査 |

段階の上げ下げは実績で決めます。同じ段階で連続合格が多いと1段上げます。連続不合格が多いと1段下げます。合否は `verify.cmd` と関門で決めます。利用制限や quota や接続障害は能力上の合否に数えません。

昇格は実績で上げ下げます（S-8.5）。新しい無料モデルは L1 から始めて、連続合格で1段上げます。昇格だけの試験は作りません。

### 5.4 モデル説明

モデルの用途と能力と難しい作業との合う説明です。資源台帳が持ちます。利用者の記述が常に優先します。

### 5.5 点検

新しい起動を止めて見直しと恒久修繕を行う時間です。点検の結果は次回の間隔に反映します。

## 6. 実行環境

### 6.1 環境

| 環境 | 意味 |
|---|---|
| `host-a` | AX の実行ホスト。ループバックの SSH で入る |
| `host-b` | 別の SSH ホスト。例は Tailscale SSH で入れる |
| `host-c` | 退避先と配備先のホスト |
| `host-d` | 一時の計算だけの借りたホスト |
| `host-e` | security-audit だけの環境 |
| `box` | Simular box。クラウドの使い捨て箱。能力 `linux-sandbox`、`web-screenshot` などを持ち、公開の内容だけを受けられる |
| `instabox` | Instabox。クラウドの使い捨て箱。同じ契約で扱う |

生きている既存の物を数えて管理する対象にしません。AX が起動した物でない常駐のコンテナは数えません。

`cloud-sandbox` の環境は、秘密と非公開の内容を受けられません。権限は限定され、特権操作を持ちません。

## 7. 窓口と決まり

### 7.1 HQ

利用者の窓口です。利用者と司令塔の対話を出します。HQ は入口を通って行き先を出します。HQ は部品を直接呼ばない。

HQ の画面は入口の受け口の `hq` のソケットから取り込みます。書き込みは入口へ `from=hq` で出します。

### 7.2 承認

戻しにくい指示を、AX が保存した内容そのものに対して、利用者本人が HQ で許す記録です。段ではありません。利用者本人の確認には（1）HQ の tailnet 身元（許可一覧の1人）と（2）承認用の第二要素が要ります。

流れは S-6.10 です。

| 項目 | 意味 |
|---|---|
| `approval_id` | 承認待ちの識別子 |
| `digest` | 正規化した JSON の SHA-256。承認の内容と保存した内容を結び付ける |
| `confirm_irreversible` | 承認を経た指示だけが `true` を持てる。司令塔の受け口は `true` を持てない |

### 7.3 情報の区分（sensitivity class）

扱う情報の最大区別です。3つに分かれます。

| 区分 | 例 |
|---|---|
| `public` | 公開リポジトリ、公開の文書 |
| `private` | 非公開リポジトリのコード |
| `sensitive` | 基盤の設定、サーバーの中身、利用者の個人情報が混じる物 |

区分の照合は1つの関数（`axcommon.policy.allowed`）にまとめます。worker-pool、管理役、グラフ検査が同じ物を使います（D-14）。

**例**：非公開リポジトリのコードは登録済みのモデルだけに回します。`cloud-sandbox` には渡しません。

### 7.4 時間の軸（timeline）

追記だけの事象の記録です。状態の表示用データは事象を先頭から読み直すと再現できます。ID は ULID（26文字）です。時刻は UTC の RFC 3339（ミリ秒まで）です。

### 7.5 モード（mode）

サブループと資源プラグインの動作モードです。4つに分かれます。timer では `collect_only_handler` がない場合、`collect_only` 中の予定を実行せずに飛ばします。

| mode | できること |
|---|---|
| `run` | 巡回も実行もする |
| `collect_only` | 巡回するが、見つけた項目は記録して待たせる |
| `poll_paused` | 巡回しない。待っている項目は起動する |
| `draining` | 巡回せず新しい実行も起動しない。実行中の物は最後まで続ける |

モードを変えても、実行中の物は止めません。制御命令の `cancel` は現在未実装です。別の `ax cancel` は ToDo またはジョブの取消を要求します。要求だけでは停止の完了を確認できません。
